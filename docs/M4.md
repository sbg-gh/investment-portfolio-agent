# M4 hybrid chat and local-model implementation

## Trust boundary and scope

This slice adds an authenticated, READ-ONLY conversational boundary on top of the M1 identity path, the M2/M2a holdings and valuation layers, and the M3 proactive machinery. It introduces a vendor-neutral local-model adapter, bounded owner-scoped context assembly, a small set of READ-ONLY specialist tools behind a deterministic schema+authorization gate, and the `ChatService` that ties them together. No network listener, background thread or real model server is added: the demo and tests drive `ChatService` entirely offline against an injectable scripted model, and the only component that may touch a live local model is the guarded benchmark script.

Identity is derived ONLY from the authenticated context. The whole turn runs through the existing `PortfolioService._run` atomic trace path with operation name `chat` and a PAYLOAD-FREE trace: no message body, holdings, symbols or sources are written, consistent with the M1 traces. A client-, chat- or model-supplied owner id is never trusted. The model is UNTRUSTED input — it only proposes; deterministic code authorizes and executes.

## THE CENTRAL SECURITY PROPERTY

Control flow is always:

```
model PROPOSAL (untrusted text)
  -> deterministic schema validation (tools.validate_proposal)
  -> a fresh M1 re-authorization (Store._authorize via the AuthContext)
  -> execution of a READ-ONLY tool
```

A malicious instruction smuggled through the user message, the assembled portfolio/instrument/memory data, or a tool result may change what the model SAYS, but it can never change what the system DOES. Every proposed tool call is re-checked against the AuthContext and a deterministic authz+schema gate BEFORE any execution; no tool executes before authorization. Security never depends on the model honoring a format: a proposal that is unparseable, aliased, malformed or cross-user is dropped and nothing executes.

## Vendor-neutral model adapter

The adapter layer (`model.py`) is framework-free and stdlib-only — it uses `urllib` and `threading`, never `openai`, `requests` or any third-party client. Runtime dependencies stay `[]`.

- `OpenAICompatibleModel(config, *, timeout=30)` POSTs a `/v1/chat/completions` request (`{model, messages:[{role:'user', content:prompt}], max_tokens}`) to `<endpoint>/v1/chat/completions` via `urllib.request` and parses the first choice's `message.content`. Any OpenAI-compatible local server (Ollama, llama.cpp, LM-compatible runtimes) is a swappable instance selected purely by env var.
- `ScriptedModel(replies)` implements the same `ports.LocalModel.generate(self, prompt, *, max_tokens) -> str` protocol by popping deterministic canned replies from a queue. It is the injectable fake that keeps the demo, eval suite and tests fully offline with no network and no live server.
- `BoundedModel(inner, config)` wraps any model with a `threading.BoundedSemaphore(config.max_concurrency)` and rejects a request whose `max_tokens` exceeds the configured output cap, so inference concurrency and output size stay bounded.

### Environment configuration

`ModelConfig.from_env(env=None)` reads the reserved adapter contract (mirroring `.env.example`):

| Variable | Default | Meaning |
|---|---|---|
| `MODEL_ENDPOINT` | `http://127.0.0.1:8080` | Base URL of the OpenAI-compatible local server |
| `MODEL_NAME` | `None` | Model identifier sent in the request body |
| `MODEL_MAX_CONCURRENCY` | `1` | Inference requests allowed at once (conservative Mac-mini bound) |
| `MODEL_CONTEXT_BUDGET` | `4096` | Maximum estimated tokens of assembled context |
| `MODEL_MAX_OUTPUT_TOKENS` | `512` | Hard cap on requested output tokens |

Non-positive or non-integer bounds raise `ValueError`. These conservative defaults target a single lightweight local model on an Apple Silicon Mac mini: one request at a time, a small context window and a bounded reply.

## Bounded, owner-scoped context assembly

`context.assemble_context(service, context, portfolio_id, *, as_of, source, budget, policy=None)` authorizes the portfolio through the M1 path (`PortfolioService` / `Store._authorize`) BEFORE any read, gathers ONLY that owner's holdings plus an M2a valuation (`valuation.value_portfolio`) with as-of time and `fresh|stale|missing` flags, serializes the result to a prompt string, and enforces the token budget. Token count is a deterministic `estimate_tokens(text)` = `ceil(len/4)` estimator (no tokenizer dependency); a prompt whose estimate exceeds `budget` raises `BoundedContextError` rather than silently exceeding the bound. Cross-user data never enters the context: assembling for one owner surfaces none of another owner's security ids or quantities, and an unauthorized `portfolio_id` is denied by re-authorization.

## Evidence rendering

Evidence reuses the M2a valuation line semantics exactly and is never fabricated. Each evidence item carries `security_id`, `status` (`fresh|stale|missing`), `market_value`, `observed_at` and the valuation `as_of`. A stale or missing line is surfaced as such — the chat boundary never invents a price, a quote or an as-of time, and it never upgrades a stale NAV to a live quote. When data is missing the status says `missing` and no value is synthesized.

## READ-ONLY specialist tools and the schema+authz gate

`tools.ToolRegistry` exposes a fixed allow-list of READ-ONLY tools the model may PROPOSE:

- `list_holdings(portfolio_id)` — wraps `PortfolioService.holdings`.
- `value_portfolio(portfolio_id, as_of, source)` — wraps `PortfolioService.value_portfolio`.

No schema contains an owner or user id argument; identity is always supplied from the AuthContext at execution time. `validate_proposal(name, args, allowed_tools)` rejects an unknown or aliased name, a missing or extra argument, or a wrong-typed argument, raising `ProposalRejected` so NOTHING executes. A validated proposal is then re-authorized through the AuthContext as the tool runs. Only READ-ONLY tools exist in M4 — there is no mutating, paper-fill or learning tool (M6 paper operations are service methods, deliberately not chat tools).

## Prompt-injection vectors and how each is refused

The deterministic gate is exercised by three injection tests, one per vector. In each the scripted model emits a malicious or cross-user proposal and the test asserts no unauthorized read, no cross-user data and no action executed:

1. Injection via the user message — a crafted message tells the model to call a tool against another user's portfolio. The proposal is schema-validated and re-authorized; the cross-user `portfolio_id` raises `PermissionError` and nothing runs.
2. Injection via data pulled into the assembled context — hostile text embedded in portfolio/instrument/memory data is framed as DATA, not instructions. Even if the model echoes it as a proposal, the gate rejects the unauthorized or malformed call.
3. Injection via a tool RESULT fed back into a later model turn — a tool result that smuggles an instruction cannot promote a new privileged or mutating call; the same validate-then-reauthorize gate drops it.

In every case a change in what the model SAYS produces no change in what the system DOES.

## No v7 schema and no conversation persistence

M4 adds NO schema migration: `SCHEMA_VERSION` stays 6. `conversation_id` is an opaque client-supplied correlation token echoed back unchanged; the response `request_id` reuses the existing payload-free `execution_traces.request_id`. Conversation messages are deliberately NOT persisted: storing message bodies, holdings, symbols or sources would record private context that AGENTS.md forbids by default, and the contract does not require durable conversation history. The payload-free `chat` trace records only operation, outcome, policy version, request id and timing — never the message or any private payload.

## Response shape

`ChatService.chat(context, *, conversation_id, message, portfolio_id=None)` returns a dictionary with exactly these keys:

- `explanation` — the model's natural-language answer, or a generic refusal when the model output is unparseable or malformed.
- `evidence` — a list of deterministic references (`security_id`, `status`, `market_value`, `observed_at`, `as_of`) reusing M2a freshness; never fabricated.
- `proposed_actions` — a list of `{name, args}` for VALIDATED, re-authorized, executed READ-ONLY tools only.
- `conversation_id` — the echoed opaque correlation token.
- `request_id` — the payload-free trace request id.

An unparseable or rejected proposal yields the generic refusal explanation and an empty `proposed_actions`, and executes nothing.

## Benchmark method

`scripts/benchmark_chat.py` is the ONLY component that may touch a live local model, and only behind a reachability probe. When Ollama is reachable on `http://localhost:11434` it runs N chat turns through `OpenAICompatibleModel` against `llama3.2:3b` (one swappable local instance of the vendor-neutral adapter), measures wall-clock latency (p50/p95) and peak RSS via `resource.getrusage`, and appends a Markdown row under the `## Chat latency benchmark` section below. When Ollama is unreachable, when invoked with `--dry-run`, or if a live run errors, it writes a clearly-labeled `UNREACHABLE` placeholder row and exits 0 with NO network. The script passes CLI args through and never fails CI; offline tests never touch Ollama.

Ollama was NOT reachable at implementation time, so the recorded row is the placeholder below. An operator with a running local model should run `PYTHONPATH=src python scripts/benchmark_chat.py` on the target Mac mini and fill the measured numbers.

## Evaluation

A deterministic M4-chat suite (`m4-chat-baseline-v1`) is wired into `PYTHONPATH=src python -m portfolio_agent.cli eval` as the fifth suite, so `cli eval` now runs five suites (safety, import-provenance, m2-completion, m3-proactive, m4-chat) and exits nonzero if any suite has a failed case. Its seven synthetic cases (`m4-001`..`m4-007`) exercise one acceptance behavior each — `offline_chat_runs_with_fake_model`, `injection_via_message_refused`, `injection_via_context_refused`, `injection_via_tool_result_refused`, `unauthorized_portfolio_denied`, `stale_evidence_shown_not_fabricated` and `bounded_context_enforced` — through the authorized services and `ChatService` driven by a `ScriptedModel` with a fixed clock for deterministic freshness.

The harness is fail-closed: `tests/test_m4_evals.py` mutates every expected answer and asserts `passed == 0` with a changed dataset hash, rejects empty/unknown/duplicate cases, and asserts the covered scenarios equal the `SCENARIOS` set. `evals/baselines/m4-chat-v1.json` records the initial deterministic result (total 7, passed 7). These are deterministic regression/correctness gates that confirm the contracts above hold; they are kept distinct from held-out learning evaluation and establish no adaptation claim (there is no `learning_improvement` key).
