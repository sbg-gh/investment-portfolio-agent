# Test-driven development and evaluation gates

For behavior changes: write an acceptance or regression test, run it against unchanged code and observe a meaningful failure, implement the smallest change that passes, then refactor with the suite green. Missing-feature imports are acceptable initial failures, but privacy and regression tests must assert behavior, not merely importability. Do not change expected outcomes to accommodate a defect. Record red/green evidence in the change description.

For this M1 change, an early implementation draft was set aside when TDD was requested. Twelve M1 acceptance tests were run against the unchanged M0 source: missing-owner isolation and future-version rejection failed, and missing M1 modules produced errors. Evaluation contract tests also failed before the harness existed. A subsequent trace-write-failure test failed against the draft because a holding had already committed; nested transactions fixed it. The final suite includes the original nine tests, thirteen M1 tests and two evaluation-harness tests.

## Run gates

```sh
PYTHONPATH=src python -m unittest discover -s tests -v
PYTHONPATH=src python -m portfolio_agent.cli demo
PYTHONPATH=src python -m portfolio_agent.cli eval
PYTHONPATH=src python -m portfolio_agent.cli eval-valuation
```

The `eval` command now runs five suites — the M1 safety baseline, the M2 import-provenance baseline, the M2-completion baseline, the M3-proactive baseline and the M4-chat baseline — and exits nonzero if any suite has a failed case.

CI installs the package, then runs all four gates on Python 3.11/3.12/3.13 and macOS/Linux. Verify installed-package evaluation too: its JSON fixtures must be bundled in the wheel. CI failures block readiness; no green GitHub run is claimed until it actually runs.

## Evaluation baseline

The versioned dataset lives in `src/portfolio_agent/eval_cases.json`. Each case starts from an isolated synthetic database and exercises the actual services. The report includes suite, policy version, canonical dataset hash, case-level expected/observed results and counts. All eight cases must pass. The harness tests deliberately replace expected answers and require every case to fail, demonstrating that results are not hard-coded passes. Empty datasets, duplicate IDs and unknown scenarios are rejected.

Cases cover cross-user access, forged identity, private retrieval, missing private owners, unauthorized public promotion, live-order denial, outside-universe holdings with a full enhanced tier, and authorized public sharing. `evals/baselines/m1-safety-v1.json` records the initial deterministic result.

These are public development/regression fixtures, NOT held-out learning evaluations. Passing does not establish financial correctness, model quality, or adaptation. In M2 add deterministic valuation/NAV/staleness datasets. In M4 add fixed tool-selection/evidence cases. In M5 maintain separately frozen held-out cases; compare no-memory, retrieval-only and approved-procedure variants without allowing evaluation outcomes into candidate memory. Follow MEMORY.md for predeclared metrics, uncertainty and promotion gates.

## M2a TDD evidence and valuation gate

Thirteen new acceptance tests were run against the M1 source before implementation; all failed with missing valuation APIs, observations/schema or evaluation module. After implementation, the full suite has 37 passing tests. The original 24 tests remain intact. Coverage includes exact decimal calculations under reduced ambient precision, price/NAV validation, freshness boundaries, late-fetched/future observations, source isolation, repeated/conflicting observations, cross-user access, snapshot replay after holdings changes, restore, v2 upgrade and trace-failure rollback.

Run `PYTHONPATH=src python -m portfolio_agent.cli eval-valuation` in addition to the M1 gates. Seven dataset-driven cases live in `src/portfolio_agent/valuation_cases.json`; the expected answers are separate from the calculation. The harness reports a dataset hash and case-level observed answers; mutation of expected answers makes all cases fail. `evals/baselines/m2-valuation-v1.json` records the initial baseline. CI executes the installed-package valuation command so missing packaged fixtures fail the build.

## M4 TDD evidence and eval gate

Each M4 behavior was driven red-first against the M3 source before implementation. The model-adapter tests failed on the missing `model` module (config defaults/env overrides, `chars/4` token estimation, scripted determinism, the concurrency bound, the output-token rejection, and the HTTP adapter exercised ONLY via a monkeypatched `urllib` opener — never the network); the tools tests failed on the missing `tools` module (unknown/aliased name, missing/extra/wrong-typed arg rejected, a well-formed proposal validated); the context tests failed on the missing `context` module (budget never exceeded, no cross-user data, unauthorized `portfolio_id` denied); the chat tests failed on the missing `chat` module (response shape, unauthorized/forged denial, payload-free trace, stale/missing evidence never fabricated); the three injection tests asserted the deterministic gate refuses a malicious or cross-user proposal with no unauthorized read, no cross-user data and no action executed; and the `tests/test_m4_evals.py` harness failed on the missing `m4_evaluation` module. After implementation the full suite passes (the previous suites remain intact, plus `tests/test_model.py`, `tests/test_tools.py`, `tests/test_context.py`, `tests/test_chat.py`, `tests/test_injection.py`, `tests/test_m4_evals.py` and `tests/test_benchmark.py`). Coverage includes the three prompt-injection vectors — injection via the user message, via portfolio/instrument/memory data pulled into the assembled context, and via a tool result fed back into a later model turn — each proving model proposal → schema validation → re-authorization refuses the call before anything executes. All model-driven tests run fully offline against `ScriptedModel`; the OpenAI-compatible HTTP path is exercised only through a monkeypatched opener, and the benchmark's offline tests never touch Ollama.

A fifth deterministic suite, `m4-chat-baseline-v1`, is wired into `cli eval` (now five suites). Seven dataset-driven cases live in `src/portfolio_agent/m4_cases.json` (`m4-001`..`m4-007`, scenarios `offline_chat_runs_with_fake_model`, `injection_via_message_refused`, `injection_via_context_refused`, `injection_via_tool_result_refused`, `unauthorized_portfolio_denied`, `stale_evidence_shown_not_fabricated`, `bounded_context_enforced`) — one per acceptance behavior, driven through the authorized services and `ChatService` with a `ScriptedModel` and a fixed clock for deterministic freshness. Expected answers are separate from the logic; `tests/test_m4_evals.py` mutates every expected answer and asserts `passed == 0` with a changed dataset hash, rejects empty/unknown/duplicate cases, and asserts the covered scenarios equal the `SCENARIOS` set and that there is no `learning_improvement` key. Mutating any expected answer makes `cli eval` exit nonzero. `evals/baselines/m4-chat-v1.json` records the initial baseline (total 7, passed 7). The guarded `scripts/benchmark_chat.py` is the only component that may touch a live local model, behind a reachability probe; with `--dry-run` or when Ollama is unreachable it writes a clearly-labeled placeholder into docs/M4.md and exits 0 with no network, verified by `tests/test_benchmark.py`. These are deterministic regression fixtures, kept distinct from held-out learning evaluation (no `learning_improvement` key); passing establishes no adaptation claim.
