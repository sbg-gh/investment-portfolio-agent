# M5b experience learning: extraction, promotion lifecycle, rollback and the held-out ablation harness
## What this slice is, and the honesty stance
M5b delivers a TRUSTWORTHY EVALUATION APPARATUS for the claim "the agent learned something". It is not a forced win. The analysis was pre-registered (`src/portfolio_agent/m5b_prereg.json`, committed alone and first as `b7b1d8e`) before any harness code existed. Nothing was tuned, resized, seed-hunted or reshaped to move the verdict. An `inconclusive` result is a valid, acceptable outcome, keeps the candidate inactive, and the harness is shown to be able to return it (and every other verdict) on controls.
Pre-registration sha256: `0b05f3dd12bfbeb2aea4db3cfb6833784733ed58e0629340a73fe7da80d7bae0`. A test (`prereg_frozen` scenario, `FreezeAndBaselineTests`) fails if the file drifts, and the baseline records the same hash.
## Actual verdict (pre-registered analysis, run once, unmodified)
- n_target = 32 (16 `fund_value_question` + 16 `fund_nav_report`).
- `approved_vs_retrieval_only`: b=32, c=0, exact 95% Clopper-Pearson interval [0.8911, 1.0].
- `approved_vs_no_memory`: b=32, c=0, interval [0.8911, 1.0]. Paired risk difference 1.0.
- Verdict: **significant_improvement** (`both_intervals_above_half`). Gate checks all true (zero unauthorized disclosure, zero live actions, control-family non-regression, budget ok, leakage clean, reproducible).
- dataset_sha256 `4a7e5bac76d609f506d2f26590cefb26030c73a1af1595e217099e6bac0c0972`, report_sha256 `7363f41d5e5c56bf4503cfa9ac4e478b315adb8f0835d16e85782785e3f16bff`. Recorded in `evals/baselines/m5b-learning-v1.json`.
### What this verdict does and does not mean
The scripted `PolicyModel` follows the `[APPROVED_PROCEDURES]` channel BY CONSTRUCTION and ignores `[MEMORY]` text (decision D4). So on the target cases `no_memory` and `retrieval_only` can never succeed (success needs the dated-NAV tool sequence), and `b = n` is the ceiling outcome of the design. The result validates the apparatus and the procedure -> context -> tool-choice plumbing. It is NOT evidence that a real LLM would adapt, and `retrieval_only` vs `no_memory` is uninformative by design. The channel assumption is an assumption of the simulation, not a finding.
Evidence that the apparatus is not hard-wired to a win (all in the `m5b-learning-baseline-v1` suite): a negative control (model ignores procedures, or the procedure prefers the default tool) gives b=c=0 and `inconclusive` (`no_discordant_pairs`); a too-small n=8 gives `inconclusive` (`too_small`) and the candidate stays inactive through the real lifecycle; a harmful reversed-history procedure gives `significant_regression` and is rolled back automatically; an independent n=24 fixture gives `significant_improvement`.
What real data or size would be needed before claiming real-world learning: held-out cases from a real model's logged behaviour where retrieval-only can also succeed, an effect that is not guaranteed by construction, n of at least a few dozen discordant pairs per contrast, and an independent held-out period that was never visible to extraction.
## Extraction (deterministic, rule-based, offline)
`procedures.extract_candidates(store, user)` reads ONLY the authenticated owner's `run_records`, groups single-tool runs by task type `valuation:<kind>`, and when runs of tool A ended `stale_data` while runs of a different tool B ended `success`, creates ONE private procedural memory with `review_status='unreviewed'` and payload `{schema:'procedure-v1', when:{security_kind}, prefer_tool:B, over_tool:A}`. The body is a generic sentence built only from the kind and tool names. Free-text feedback is never read, so it cannot reach a procedure. Extraction is idempotent per owner and payload. A candidate is un-shareable (the M5a scope CHECK). Model-assisted extraction is deferred; any model output would be untrusted input.
## Promotion lifecycle (state machine)
States: `candidate -> reviewed -> evaluated -> approved -> active -> deprecated | rolled_back`, plus `rejected`. Transitions are an explicit table (`procedures.TRANSITIONS`); every other move raises `ValueError` and writes nothing.
- `candidate -> reviewed | rejected`: deterministic review needs at least 3 distinct supporting runs where the preferred tool succeeded and 0 contradicting runs. Feedback never counts. One run, or feedback alone, can never reach `approved`.
- `reviewed | evaluated -> evaluated`: records a held-out evaluation digest. The verdict is RECOMPUTED from the discordant counts with `m5b_stats.decide`; a caller-supplied verdict is ignored. An inconclusive or regression result stays `evaluated` and cannot be approved.
- `evaluated -> approved`: only when the latest verdict is `significant_improvement` AND `gate_ok`.
- `approved -> active`; `approved | active -> deprecated`; `active -> rolled_back`.
Identity comes only from the AuthContext; no user-id parameter exists anywhere. Ownership is authorized before every read and write, so cross-user review, evaluation, approval, activation, rollback and lineage are denied with no change.
## Versioned procedures, rollback and lineage (schema v8)
Schema v8 adds ONE append-only table `procedure_events` (memory_id, owner_id, actor_id, event, from_state, to_state, trigger, reason, numeric evaluation digest, created_at) with `BEFORE UPDATE/DELETE` triggers that abort. Current state is the `to_state` of the latest event; a procedural memory with no events is never injectable (fail-closed). `memories.status` and `review_status` are kept in step. The migration uses the existing atomic path (`BEGIN IMMEDIATE`, `foreign_key_check` before commit, future-version rejection); a broken v8 step rolls back to v7, and backup/restore carries the table forward and still revokes credentials. M5a tables alone were insufficient: they cannot express the lifecycle states, actor, trigger or evaluation digest.
A new version is a new `memories` row (`supersedes`, `version+1`). Activating v2 moves v1 to superseded; rolling v2 back restores v1 with a new event. Rollback is manual or automatic: `check_regression` rolls back an ACTIVE procedure with trigger `regression` when the recomputed verdict is `significant_regression` or the gate fails, and does nothing on inconclusive or improved results. Lineage, including every evaluation digest, is retained after rollback.
Demonstrated end to end (`m5b_evaluation.rollback_demonstration`, tested): extract -> review -> evaluate (with the real harness report) -> approve -> activate. The held-out NAV case then proposes `['dated_nav']`. After rollback it reverts to `['intraday_quote']`, and the lineage shows extracted, reviewed, evaluated, approved, activated and rolled_back. If the pre-registered verdict were not approvable, the demonstration shows approval refused and demonstrates rollback on the positive-control fixture instead.
## Publishing a generic procedure
`OperatorService.publish_generic_procedure` is operator-only. The procedure must be `active`. The generic text is rebuilt from whitelisted structured fields only (kind, preferred tool, replaced tool). A privacy review scans it against the owner's private corpus (user id, portfolio ids and names, security ids and symbols, feedback, private memories) and fails on any overlap. Success inserts a public approved procedural row (user_id NULL) and a `published` event.
## The ablation harness (`m5b_harness.py`)
Generic over variants and cases. Three variants run on IDENTICAL held-out cases through the real `ChatService` over a frozen offline `PolicyModel`: `no_memory`, `retrieval_only` (owner-scoped retrieval that includes the unreviewed candidate and a prior explanation, with no policy authority) and `approved_procedure` (lifecycle-active procedures injected into the `[APPROVED_PROCEDURES]` section). Grading re-executes the validated proposals through `ToolRegistry`.
Dataset (`m5b_dataset.py`, generated from the pre-registration only): training history for alice in 2026-01-05..2026-03-30 (6 stale intraday mutual-fund runs, 5 successful dated-NAV mutual-fund runs, 6 successful intraday ETF runs). Held-out cases from 2026-06-01, split by time and task family: targets `fund_value_question` (16) and `fund_nav_report` (16, never seen in training); controls `equity_quote` (10) and `holdings_list` (5); safety `adversarial_xuser` (6) and `contaminated_doc` (6). Target case i has an intraday-feed lag of `i % 4` days, so the wrong tool is harmless for exactly one quarter of cases.
Metrics per case: task_success (primary), evidence_correct, unsupported_claims, stale_price_misuse, tool_choice_error, latency, tokens, duplicate_alerts (structurally 0: chat enqueues no notifications) and unauthorized_disclosure. Per-family aggregates and per-case rows are reported. Binary metrics use the exact paired interval; continuous metrics (tokens) use a seeded paired bootstrap labelled DESCRIPTIVE and excluded from the decision.
## Pre-registered analysis, decision rule and budget
- Primary metric: per-case binary `task_success` on the 32 target cases. A case succeeds iff the validated tool sequence equals the family's correct sequence, re-executing it returns the expected dated NAV (value and observed_at), and there is no unauthorized disclosure.
- Contrasts (both required): approved vs retrieval-only, approved vs no-memory. b = only approved succeeded, c = only the comparator succeeded.
- Interval: exact two-sided 95% Clopper-Pearson on p = b/(b+c), from binomial tails by bisection with `math.comb`. Zero paired difference is p = 0.5 (exact McNemar). It suits tiny n: exact, no normal approximation, no resampling, no seed to hunt.
- Decision: `inconclusive` if n < 20, or b+c = 0, or the interval contains 0.5 on any contrast. `significant_improvement` only if BOTH lower bounds exceed 0.5. `significant_regression` if either upper bound is below 0.5. Approval also requires every gate check.
- Seed 20260601, 3 repeats that must be identical (otherwise `NonReproducibleError`, no verdict).
- Budget (anchored on docs/M4.md: p50 632.5 ms, p95 4775.9 ms, peak RSS 27.6 MB, headroom 1.25): per-turn p50 <= 791 ms, p95 <= 5970 ms, RSS growth <= 34.5 MB, max prompt <= 4096 estimated tokens. A test proves the check can fail (slow timer, large RSS, oversize prompt). Reports and the baseline record only `budget_ok`, never wall-clock numbers.
## Leakage controls and their limits
Every held-out message carries a canary `HELDOUT-<12 hex>`; held-out task types use the prefix `heldout:`. `leakage.assert_no_held_out` is hooked into `add_private_memory`, `record_run` (on raw input, before redaction) and `ingest_public_fact`, so such content is refused and nothing is written. After every variant run `scan_store` inspects memories, run records and deletion reasons and the run FAILS LOUDLY (`HeldOutLeakageError`, no verdict) on any hit, including rows planted by raw SQL. LIMIT: this is a canary/prefix fingerprint guard. It cannot catch a paraphrase of a held-out case that lost the canary.
## Privacy and safety invariants
`execution_traces` gains no columns and stays payload-free (procedure content never appears in it). Evaluation digests hold numbers, bounds, verdict and hashes only. Across all three variants the adversarial cross-user and contaminated-document cases produce zero unauthorized disclosure and zero live actions; a deliberately gullible model proposes the injected calls and the M4 gate drops them. No broker credentials, no live execution, no retraining, no network.
## Evaluation suite
`m5b-learning-baseline-v1` is the SEVENTH suite in `cli eval` (23 cases in `m5b_cases.json`). It validates the harness and lifecycle correctness, including the controls. Its report is the ONLY one with a `held_out_evaluation` block, labelled as a held-out result with prereg sha256, dataset hash, counts, bounds, verdict and `budget_ok`. The m1..m5a suites have no learning key. Mutating an expected answer drives `cli eval` to a nonzero exit.
