# M3 proactive service implementation

## Trust boundary and scope

This slice adds durable background work on top of the M1 authenticated boundary, the M2a valuation layer and the M2 coverage bookkeeping. It introduces a deterministic, test-invokable job runner, a notification outbox, per-user preferences and a minimal set of monitoring rules. No network listener, background thread or real notification channel is added: the demo and tests drive the scheduler explicitly, and delivery is an in-memory sink.

Identity is still derived only from the authenticated context or a trusted owner reference, never from a job payload, chat, model or request body. A job carries a trusted `owner_ref` (for private work) or a `public_scope` (for holder-blind public work), never a caller-asserted identity. A private monitoring job RE-AUTHORIZES the current owner of its portfolio at execution time: a job enqueued earlier re-checks the portfolio's current owner when it runs, so an ownership change after enqueue means the job never reads or notifies on the old owner's private data. `Store` remains the internal persistence layer for offline administration, not an authentication boundary.

Job rows, outbox rows, monitoring state and traces stay payload-free: they carry operation/type/keys/status/timestamps only, never symbols, quantities, holdings or sources, consistent with the M1 traces. Timestamps are UTC ISO-8601; all comparisons use Decimal.

## Durable job store, leases, retry and dead-letter

`jobs.py` exposes a durable job store over the existing `Store.transaction()` (BEGIN IMMEDIATE) with named module constants: `LEASE_SECONDS = 300` (mirroring the five-minute auth-context ceiling), `MAX_ATTEMPTS = 3` and `MAX_CLAIM_PER_TICK = 8`.

`JobStore.enqueue(job_type, *, idempotency_key, due_at, correlation_id, owner_ref=None, public_scope=None)` inserts one durable job and dedups on `(type, idempotency_key)`, returning the prior id on a repeat. Exactly one of `owner_ref`/`public_scope` must be set (XOR). `claim_due(now, limit)` atomically claims due pending jobs and expired-lease leased jobs, setting `status='leased'`, `lease_expires_at = now + LEASE_SECONDS` and `attempts += 1`. `complete(job_id)` marks `done`; `fail(job_id, now)` re-arms a job as immediately due again (deterministic due-time only, no backoff) or routes it to `dead` once `attempts >= MAX_ATTEMPTS`. `recover_expired(now)` resets expired leases back to pending; `review_queue()` lists `dead` jobs for operator review. The dead-letter/review queue is a `status='dead'` VALUE on the jobs table (`status IN ('pending','leased','done','dead')`), not a separate table.

`JobRunner(store, handlers)` is a deterministic, test-invoked poller. `handlers` is a `{job_type: callable(job_row, store, now)}` registry passed at construction (peers are discovered, not hardcoded). `tick(now)` delegates to `run_due(now)`, which recovers expired leases, claims due jobs, and dispatches each inside `store.transaction()`: a normal return calls `complete()`, an exception calls `fail()`. One handler failure never aborts the tick. `build_default_handlers(store)` returns `{'collect': collect_handler, 'monitor_portfolio': monitor_portfolio_handler}`.

Crash/resume-without-duplicate relies on an idempotent handler: an effect applied before a crash is not re-applied on the resumed tick, and the lease+recover machinery guarantees the job resumes and ends `done` without a second concurrent claim inside the lease window. Exhausting `MAX_ATTEMPTS` routes to `dead` and the job is never claimed again.

## Notification outbox and delivery semantics

The outbox reuses the `ports.Notifier` protocol. `Store.enqueue_notification(user_id, event, *, dedup_key, channel, now, materiality=None)` PERSISTS one `notification_outbox` row before any delivery (at-least-once). Deduplication is enforced at the schema level by `UNIQUE(user_id, dedup_key)`: a second enqueue for an existing `(user_id, dedup_key)` returns the prior id and writes nothing, so a retried job never double-sends. Suppression is evaluated at enqueue time with precedence quiet-hours → materiality-below-threshold → cooldown; the first match stores `delivery_status='suppressed'`, otherwise `pending`. `event` is a fixed label; no symbol/quantity/holding is ever stored.

`Store.deliver_pending(notifier, now)` walks `pending` rows in insertion order, calls `notifier.notify(user_id, event, deduplication_key=dedup_key)`, and marks each `sent`; `suppressed` rows are never delivered. `LocalSinkNotifier` (`notifier.py`) is a deterministic in-memory sink, NOT a real channel or network adapter: it records `(user_id, message, deduplication_key)` once per unseen `(user_id, dedup_key)`, so an at-least-once retry appends no duplicate. The at-least-once guarantee therefore relies on the notifier's dedup set plus the outbox `UNIQUE` constraint.

## Per-user preferences

`notification_preferences` is keyed by `user_id` and carries `quiet_start`/`quiet_end` (UTC hours or both NULL), a `materiality_threshold` Decimal (stored as text), `cooldown_seconds` and a `channel` (default `local-sink`). `PortfolioService.set_preferences` and `preferences` derive and authorize the user from the trusted context through the atomic trace path — never a caller-supplied owner id. A forged or cross-user context is denied (PermissionError) and a failed action records a metadata-only `invalid` trace with no preferences payload. The quiet window is half-open `[quiet_start, quiet_end)` and wraps past midnight.

## Deterministic monitoring rules

`monitoring.py` holds two pure evaluators that read ONLY existing data (holdings, baseline_coverage, market_observations) and never fabricate a value:

- `evaluate_stale_coverage(store, security_id, now, policy=None)` returns `fresh | stale | missing`, reusing `valuation.FreshnessPolicy` (price window for stock/ETF, NAV window for mutual funds) exactly as `value_portfolio` surfaces staleness. No observation means `missing`, never a synthesized price.
- `evaluate_materiality(store, security_id, threshold)` compares the two most recent observations' Decimal change ratio against the per-user threshold, returning `('crossed'|'within', ratio_text)`. Fewer than two observations, or a zero prior, yields `('within', '0')`.

`monitor_portfolio_handler` decodes and re-authorizes the owner, loads preferences, reads the portfolio's held + baseline-covered securities, and for each evaluates both rules against the recorded `monitoring_state`. It records new state and enqueues an owner-scoped outbox item ONLY on a state CHANGE (and only when stale is not `fresh` or materiality is `crossed`). A return to `fresh`/`within` records state but enqueues nothing. Because `monitoring_state` is keyed deterministically by `(security_id, rule)`, re-evaluating identical inputs produces NO new notification — unchanged conditions stay quiet. The dedup key `user|security|rule|state` is deterministic, so a retry over the same state reuses the key and cannot double-notify. Richer rules (concentration, allocation drift, corporate actions) are deferred.

## Public coalescing and owner-scoped private analysis

Public collection coalesces by `(security, source, time-bucket)` via `monitoring.coalesce_public_collection`, so the public step runs once per key regardless of how many users hold the security; the plan carries no holder identity. `collect_handler` is intentionally holder-blind: it reads no holdings and enqueues no outbox item. The subsequent private per-user analysis (`monitor_portfolio_handler`) and the outbox stay separate and owner-scoped, so collection never reveals which users hold an instrument.

## Schema upgrades (v6)

`PRAGMA user_version` continues to track migrations: v1 legacy, v2 memory scope/credentials/traces, v3 observations/snapshots, v4 import provenance, v5 ledger/admission/coverage, and v6 (this slice) adds four tables and leaves all v1–v5 tables and triggers untouched:

- `jobs` — durable jobs `(id, type, owner_ref, public_scope, idempotency_key, due_at, lease_expires_at, attempts, status, correlation_id, created_at)` with `status IN ('pending','leased','done','dead')`, a `CHECK((owner_ref IS NOT NULL) <> (public_scope IS NOT NULL))` XOR, `UNIQUE(type, idempotency_key)`, and an index on `(status, due_at)`. Payload-free.
- `notification_outbox` — `(id, user_id, event, dedup_key, channel, delivery_status, created_at)` with `delivery_status IN ('pending','sent','suppressed')`, `UNIQUE(user_id, dedup_key)` and an index on `(user_id, created_at)`.
- `notification_preferences` — `(user_id PK, quiet_start, quiet_end, materiality_threshold, cooldown_seconds, channel, created_at)`.
- `monitoring_state` — `(security_id, rule, state_key, observed_at, created_at, PRIMARY KEY(security_id, rule))`.

The upgrade runs under a single immediate transaction. If any DDL or data step fails, the whole upgrade rolls back and `user_version` stays at v5 with existing data intact (a broken v6 script leaves v5 and its holdings/ledger untouched). A foreign-key check runs before commit. A database whose version is newer than the application is rejected rather than opened. `backup.py` reads `SCHEMA_VERSION` (no hardcoded literal), so the exact-schema check follows the bump automatically.

## Backup and recovery

`backup(store, new_path)` and `restore(snapshot_path, new_path)` carry the v6 tables forward: a restored database preserves `jobs`, `notification_outbox`, `notification_preferences` and `monitoring_state` alongside the v1–v5 tables, and passes integrity, foreign-key and exact-schema checks. As in M1, restore revokes every credential so recovery cannot resurrect old access; re-provision users through trusted administration afterward. Neither helper overwrites an existing file.

## Evaluation

A deterministic M3-proactive suite (`m3-proactive-baseline-v1`) is wired into `PYTHONPATH=src python -m portfolio_agent.cli eval` as the fourth suite, so `cli eval` now runs four suites (safety, import-provenance, m2-completion, m3-proactive) and exits nonzero if any suite has a failed case. Its six synthetic cases (`m3-001`..`m3-006`) exercise the four acceptance gates plus reauthorize-at-execution and dedup through the authorized stack and the job runner: a crashed/resumed job applies its effect once (`single_effect`); an outbox item for user A never reaches user B (`isolated`); two monitor runs over identical inputs produce one notification (`quiet`); a stale observation surfaces as stale and is never fabricated (`stale_shown`); a job whose owner changed after enqueue does not act on the old private data (`denied`); and a retried enqueue/delivery does not double-send (`single_send`).

The harness is fail-closed — `tests/test_m3_evals.py` mutates every expected answer and asserts `passed == 0` with a changed dataset hash, and rejects empty/unknown/duplicate cases. `evals/baselines/m3-proactive-v1.json` records the initial deterministic result. These are deterministic regression/correctness gates that confirm the contracts above hold; they are kept distinct from held-out learning evaluation and establish no adaptation claim (there is no `learning_improvement` key).
