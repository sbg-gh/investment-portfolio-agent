# M2 import provenance and reconciliation implementation

## Trust boundary and scope

This slice adds audited holding lifecycle on top of the M1 authenticated boundary and the M2a valuation layer. Application callers use `PortfolioService` with a context from `Authenticator.authenticate(token)`; no method accepts a caller-supplied owner ID. Identity is derived from the context, ownership is authorized before every read, write and receipt retrieval, and a forged or cross-user context is denied. `Store` remains the internal persistence layer for offline administration, not an authentication boundary.

Implemented in this slice:

- Audited, explicit holding removal with reconciliation. Removing a holding that does not exist raises an error rather than silently succeeding, so a desync between an external feed and local state surfaces instead of being overwritten.
- Import provenance: every provenance-bearing import or removal records an `import_receipt` carrying the public `source` and the `market_as_of` cutoff, plus a `holding_event` forming the audit trail.
- Effective-dated instrument aliases: a symbol maps to an already-registered security over a `[effective_from, effective_to)` window, resolved as of a date.
- Idempotent import and removal keyed on a caller-supplied `(portfolio_id, idempotency_key)`; a repeated or retried call returns the prior result without re-applying.

Out of scope and still-incomplete M2 work: transactions and lot-level accounting, baseline-collection scheduling, capacity-enhancement admission queues, and real provider integration. Those remain planned. The research target of 400 and the 75-slot enhanced-monitoring tier stay independent of valid holdings; neither limits holdings or the security master. Alias registration and provenance imports resolve only against already-registered securities or the fixture validator — they never invent identifiers or prices. Real provider integration follows only after coverage, licensing and freshness rules are reviewed.

## Service contracts

`PortfolioService.import_holding_with_provenance(context, portfolio_id, symbol, quantity, *, source, market_as_of, idempotency_key)` authorizes ownership, resolves identity (alias first, then validator), upserts the holding, and records a receipt and a holding event atomically. It returns the resolved `security_id`. `source` and `idempotency_key` must be non-empty; `quantity` must be a positive finite decimal.

`PortfolioService.remove_holding(context, portfolio_id, security_id, *, source, idempotency_key, market_as_of)` authorizes ownership, deletes the holding, and records an audited `remove` receipt and event. Removing a holding that is not present raises a reconciliation `ValueError` with no side effects.

`PortfolioService.receipts(context, portfolio_id)` returns that owner's receipts as `(id, security_id, source, market_as_of, quantity, action)` rows ordered by insertion.

All three reuse the M1 atomic success/failure trace path: a successful mutation and its execution trace commit together; a failed action rolls back to the inner savepoint, after which a metadata-only outcome (`denied`, `invalid` or `error`) is still recorded. Traces continue to omit symbols, quantities, portfolio names and payloads.

`Store.register_alias(symbol, security_id, source, effective_from, effective_to=None)` is trusted internal administration used by fixtures, not an authenticated service method. It rejects an unregistered target security and an inverted or empty window (`effective_to` must be strictly after `effective_from`).

### Alias resolution precedence

`Store.resolve_alias(symbol, as_of)` runs BEFORE the authoritative validator during a provenance import. It maps a symbol only to an already-registered security and never auto-registers, never overrides and never invents authoritative identity. On a miss it returns `None`, and the import falls through to the validator, which resolves and registers the instrument as usual. The window is half-open `[effective_from, effective_to)`: `effective_from` is inclusive, `effective_to` is exclusive, and an open-ended alias has no upper bound. When several aliases for the same symbol overlap a date, the newest `effective_from` wins (ties broken by insertion order). An alias thus changes which already-known security a symbol binds to over time; it is never a substitute for authoritative validation of an unknown instrument.

## Local composition example

```python
from datetime import datetime, timezone
from portfolio_agent.auth import Authenticator
from portfolio_agent.core import Store, FixtureValidator, ValidatedSecurity
from portfolio_agent.services import PortfolioService

store = Store()  # in-memory; use a protected local path for persistence
try:
    store.create_user('alice')  # trusted bootstrap only
    auth = Authenticator(store)
    context = auth.authenticate(auth.provision('alice'))  # return token securely; do not log
    validator = FixtureValidator({
        'DEMO': ValidatedSecurity('s0', 'DEMO', 'stock', 'US', 'synthetic'),
    })
    app = PortfolioService(store, auth, validator)
    portfolio = app.create_portfolio(context, 'Synthetic example')

    cutoff = datetime(2026, 11, 6, 21, tzinfo=timezone.utc)

    # Idempotent provenance import: the retry with the same key does not re-apply.
    sid = app.import_holding_with_provenance(
        context, portfolio, 'DEMO', '1.5',
        source='synthetic-feed', market_as_of=cutoff, idempotency_key='k1')
    app.import_holding_with_provenance(
        context, portfolio, 'DEMO', '9',  # ignored: same (portfolio, key)
        source='synthetic-feed', market_as_of=cutoff, idempotency_key='k1')
    assert app.holdings(context, portfolio) == [('s0', '1.5')]
    assert len(app.receipts(context, portfolio)) == 1

    # Register an effective-dated alias to an already-registered security, then
    # resolve a symbol the validator does not know as of a date.
    store.register(ValidatedSecurity('aliased', 'REAL', 'stock', 'US', 'synthetic'))
    alias_from = datetime(2026, 1, 1, tzinfo=timezone.utc)
    store.register_alias('GHOST', 'aliased', 'synthetic', alias_from)
    assert store.resolve_alias('GHOST', cutoff) == 'aliased'
    assert store.resolve_alias('GHOST', datetime(2025, 1, 1, tzinfo=timezone.utc)) is None

    # Audited removal: deletes the holding and records a 'remove' receipt/event.
    app.remove_holding(context, portfolio, sid,
                       source='synthetic-feed', idempotency_key='rm1', market_as_of=cutoff)
    assert app.holdings(context, portfolio) == []
    assert any(action == 'remove' for *_, action in app.receipts(context, portfolio))
finally:
    store.close()
```

## Schema upgrades

`PRAGMA user_version` continues to track migrations: v1 is the legacy schema, v2 adds memory scope, credentials and execution traces, v3 (M2a) adds `market_observations` and `valuation_snapshots`, and v4 adds the import-provenance tables. A fresh database ends at v4.

v4 adds three tables and leaves `holdings` unchanged as the current-state snapshot:

- `import_receipts` — one row per applied import or removal, with `(portfolio_id, security_id, idempotency_key, source, market_as_of, quantity, action)` and `action` constrained to `upsert` or `remove`. `UNIQUE(portfolio_id, idempotency_key)` enforces idempotency at the schema level.
- `holding_events` — the append-only audit trail, each row an `import` or `remove` event referencing its originating receipt.
- `security_aliases` — `(symbol, security_id, source, effective_from, effective_to)` windows backing effective-dated resolution.

The upgrade runs under a single immediate transaction. If any DDL or data step fails, the whole upgrade rolls back and `user_version` stays at v3 with existing holdings, observations and snapshots intact. A foreign-key check runs before commit. A database whose version is newer than the application is rejected rather than opened. Back up an existing database before opening it with new code; the backup helper accepts only current-schema databases and does not silently upgrade archives.

## Backup and recovery

`backup(store, new_path)` and `restore(snapshot_path, new_path)` carry the v4 tables forward: a restored database preserves `import_receipts`, `holding_events` and `security_aliases` alongside holdings, observations and snapshots, and passes integrity, foreign-key and exact-schema checks. As in M1, restore revokes every credential so recovery cannot resurrect old access; re-provision users through trusted administration afterward. Neither helper overwrites an existing file.

## Idempotency and reconciliation semantics

Repeated or retried imports and removals dedupe on `(portfolio_id, idempotency_key)`. Before applying, the Store looks up an existing receipt for the key; if one is present it returns the prior `security_id` and makes no further change, so a different quantity submitted under an already-used key is ignored rather than overwriting the holding. Each applied action records exactly one receipt and one holding event, giving an auditable count that does not grow on retry. A new key applies again as a distinct action.

Receipts record the public `source` and the `market_as_of` cutoff (normalized to UTC ISO-8601) so each change states what fed it and as of when. Removal is explicit and audited: deleting a holding writes a `remove` receipt with a null quantity and a `remove` holding event. Removing a holding that is not present raises a reconciliation error and writes nothing — there is no silent success — so divergence between an external source and local state is surfaced for reconciliation. Together, `holding_events` form the ordered audit trail linking every current-state change back to the receipt that caused it.

## Evaluation

A deterministic import-provenance suite (`m2-import-provenance-baseline-v1`) is wired into `PYTHONPATH=src python -m portfolio_agent.cli eval` alongside the existing safety suite; both must pass for the command to exit zero. Its synthetic cases cover an import receipt recording source and as-of, an effective-dated alias binding a symbol the validator does not know, idempotent retry applying only once, and audited explicit removal. The report records the policy version and a dataset hash. These are regression/correctness gates that confirm the contracts above hold; they are not held-out evidence of learning, adaptation or investment results.
