# M2 import provenance and reconciliation implementation

## Trust boundary and scope

This slice adds audited holding lifecycle on top of the M1 authenticated boundary and the M2a valuation layer. Application callers use `PortfolioService` with a context from `Authenticator.authenticate(token)`; no method accepts a caller-supplied owner ID. Identity is derived from the context, ownership is authorized before every read, write and receipt retrieval, and a forged or cross-user context is denied. `Store` remains the internal persistence layer for offline administration, not an authentication boundary.

Implemented in this slice:

- Audited, explicit holding removal with reconciliation. Removing a holding that does not exist raises an error rather than silently succeeding, so a desync between an external feed and local state surfaces instead of being overwritten.
- Import provenance: every provenance-bearing import or removal records an `import_receipt` carrying the public `source` and the `market_as_of` cutoff, plus a `holding_event` forming the audit trail.
- Effective-dated instrument aliases: a symbol maps to an already-registered security over a `[effective_from, effective_to)` window, resolved as of a date.
- Idempotent import and removal keyed on a caller-supplied `(portfolio_id, idempotency_key)`; a repeated or retried call returns the prior result without re-applying.

The M2 close-out (schema v5) adds the remaining pieces: a signed transaction ledger that reconciles to the holdings snapshot, deterministic baseline coverage, and the operator-gated enhanced-monitoring admission machine (see the sections below). Still deferred: tax lots, cost basis, cash and fees (M6); durable baseline-collection scheduling, leases, outbox and retry (M3); and real provider integration (only after coverage, licensing and freshness rules are reviewed). The research target of 400 and the 75-slot enhanced-monitoring tier stay independent of valid holdings; neither limits holdings or the security master. Alias registration and provenance imports resolve only against already-registered securities or the fixture validator — they never invent identifiers or prices.

## Service contracts

`PortfolioService.import_holding_with_provenance(context, portfolio_id, symbol, quantity, *, source, market_as_of, idempotency_key)` authorizes ownership, resolves identity (alias first, then validator), upserts the holding, and records a receipt and a holding event atomically. It returns the resolved `security_id`. `source` and `idempotency_key` must be non-empty; `quantity` must be a positive finite decimal.

`PortfolioService.remove_holding(context, portfolio_id, security_id, *, source, idempotency_key, market_as_of)` authorizes ownership, deletes the holding, and records an audited `remove` receipt and event. Removing a holding that is not present raises a reconciliation `ValueError` with no side effects.

`PortfolioService.receipts(context, portfolio_id)` returns that owner's receipts as `(id, security_id, source, market_as_of, quantity, action)` rows ordered by insertion.

All three reuse the M1 atomic success/failure trace path: a successful mutation and its execution trace commit together; a failed action rolls back to the inner savepoint, after which a metadata-only outcome (`denied`, `invalid` or `error`) is still recorded. Traces continue to omit symbols, quantities, portfolio names and payloads.

`Store.register_alias(symbol, security_id, source, effective_from, effective_to=None)` is trusted internal administration used by fixtures, not an authenticated service method. It rejects an unregistered target security and an inverted or empty window (`effective_to` must be strictly after `effective_from`).

### Alias resolution precedence

`Store.resolve_alias(symbol, as_of)` runs BEFORE the authoritative validator during a provenance import. It maps a symbol only to an already-registered security and never auto-registers, never overrides and never invents authoritative identity. On a miss it returns `None`, and the import falls through to the validator, which resolves and registers the instrument as usual. The window is half-open `[effective_from, effective_to)`: `effective_from` is inclusive, `effective_to` is exclusive, and an open-ended alias has no upper bound. When several aliases for the same symbol overlap a date, the newest `effective_from` wins (ties broken by insertion order). An alias thus changes which already-known security a symbol binds to over time; it is never a substitute for authoritative validation of an unknown instrument.

## Local composition example

```python
from datetime import datetime, timezone
from portfolio_agent.auth import Authenticator
from portfolio_agent.core import Store, FixtureValidator, ValidatedSecurity
from portfolio_agent.services import PortfolioService

store = Store()  # in-memory; use a protected local path for persistence
try:
    store.create_user('alice')  # trusted bootstrap only
    auth = Authenticator(store)
    context = auth.authenticate(auth.provision('alice'))  # return token securely; do not log
    validator = FixtureValidator({
        'DEMO': ValidatedSecurity('s0', 'DEMO', 'stock', 'US', 'synthetic'),
    })
    app = PortfolioService(store, auth, validator)
    portfolio = app.create_portfolio(context, 'Synthetic example')

    cutoff = datetime(2026, 11, 6, 21, tzinfo=timezone.utc)

    # Idempotent provenance import: the retry with the same key does not re-apply.
    sid = app.import_holding_with_provenance(
        context, portfolio, 'DEMO', '1.5',
        source='synthetic-feed', market_as_of=cutoff, idempotency_key='k1')
    app.import_holding_with_provenance(
        context, portfolio, 'DEMO', '9',  # ignored: same (portfolio, key)
        source='synthetic-feed', market_as_of=cutoff, idempotency_key='k1')
    assert app.holdings(context, portfolio) == [('s0', '1.5')]
    assert len(app.receipts(context, portfolio)) == 1

    # Register an effective-dated alias to an already-registered security, then
    # resolve a symbol the validator does not know as of a date.
    store.register(ValidatedSecurity('aliased', 'REAL', 'stock', 'US', 'synthetic'))
    alias_from = datetime(2026, 1, 1, tzinfo=timezone.utc)
    store.register_alias('GHOST', 'aliased', 'synthetic', alias_from)
    assert store.resolve_alias('GHOST', cutoff) == 'aliased'
    assert store.resolve_alias('GHOST', datetime(2025, 1, 1, tzinfo=timezone.utc)) is None

    # Audited removal: deletes the holding and records a 'remove' receipt/event.
    app.remove_holding(context, portfolio, sid,
                       source='synthetic-feed', idempotency_key='rm1', market_as_of=cutoff)
    assert app.holdings(context, portfolio) == []
    assert any(action == 'remove' for *_, action in app.receipts(context, portfolio))
finally:
    store.close()
```

## Transaction ledger and reconciliation (v5)

`Store.record_transaction(user_id, portfolio_id, security_id, side, quantity, *, source, idempotency_key, occurred_at)` appends one signed buy/sell event to `transactions`. It authorizes ownership, validates `side ∈ {buy, sell}`, a positive finite Decimal `quantity`, and non-empty `source`/`idempotency_key`, and normalizes `occurred_at` to a UTC ISO-8601 string. It is idempotent on `(portfolio_id, idempotency_key)`: a retry returns the prior transaction id and writes nothing new. It never auto-mutates `holdings` — the ledger is a separate event stream, not a driver of current state. `transactions(user_id, portfolio_id)` returns that owner's rows ordered by insertion.

`Store.reconcile_portfolio(user_id, portfolio_id)` computes the signed Decimal sum per `(portfolio_id, security_id)` — buy adds, sell subtracts — and compares it to the holdings snapshot quantity, returning `(security_id, ledger_sum_text, holding_qty_text_or_None, reconciled_bool)` rows. "Financial fixtures reconcile" means that for a fixture where the signed ledger sum equals the snapshot, every row reports `reconciled=True`. A divergence (including a security present only in the ledger, which yields `holding_qty=None`) reports `reconciled=False`; reconciliation flags the mismatch and never coerces the snapshot. All arithmetic is Decimal. Tax lots, cost basis, cash and fees are deferred to M6.

`PortfolioService.record_transaction`, `transactions` and `reconcile` wrap these through the atomic trace path with fixed, payload-free operation names; cross-user and forged-context access is denied, and a failed action records a metadata-only `invalid` trace carrying no side/quantity/source.

## Baseline coverage (v5)

Baseline coverage is maintained atomically with the holding lifecycle, independent of the monitoring tier. Inside the same transaction as the holding upsert, `import_holding`/`import_holding_with_provenance` INSERT OR IGNORE a `baseline_coverage` row (`covered=1`, `since` = the import cutoff when available else a UTC now). `remove_holding` recomputes whether any portfolio still holds the security and, when none does, deletes the coverage row so the covered-set equals the distinct-held-securities-set exactly. A security held by two portfolios keeps coverage until the last holder is removed. An outside-universe holding stays covered even with the enhanced tier and its queue full. `Store.baseline_coverage(security_id)` returns the covered flag (public status, no private context); `Store.reconcile_baseline_coverage()` asserts covered-set == held-set and returns discrepancies (`held_without_coverage` / `coverage_without_holder`), empty when consistent. M2 answers "is every held security covered?"; durable collection scheduling (leases/outbox/retry) is M3.

## Enhanced-monitoring admission queue (v5)

`Store.propose_enhancement(security_id, *, reason, operator, now, queue_capacity=ADMISSION_QUEUE_CAPACITY)` is a deterministic admit → queue → reject machine with no auto-eviction, using integer counts only. The first `MONITORING_CAPACITY` (75) distinct securities are `admitted` into the active `monitoring` set and recorded with an `admitted` admission row (position NULL). The next distinct securities are `queued` FIFO (position = next index, `proposed_at` = `utc(now).isoformat()`) up to `ADMISSION_QUEUE_CAPACITY` (default 25). Beyond that the proposal is `rejected` and nothing is written. Re-proposing an already admitted/queued security is idempotent (`monitoring_admissions.security_id` is unique): it returns the current state and adds no row. The 76th distinct enhancement is therefore queued, not active — rejected from the active tier. The existing `monitoring` table and `monitoring_cap` trigger stay the active-set source of truth, untouched. `Store.monitoring_admissions()` lists admitted first, then queued FIFO by position, tie-break on the stable `security_id`.

`OperatorService.propose_enhancement(context, security_id, *, reason)` and `list_monitoring(context)` expose this over the authorized boundary: operator-gated (a non-operator context is denied and writes nothing), operator identity derived from the context, UTC `now` computed at the boundary, both through the atomic trace path with payload-free operation names. The existing `enable_monitoring`/`set_research` operator methods remain for back-compat. A full tier and full queue never block a valid holding import — admission and holdings are independent.

## Schema upgrades

`PRAGMA user_version` continues to track migrations: v1 is the legacy schema, v2 adds memory scope, credentials and execution traces, v3 (M2a) adds `market_observations` and `valuation_snapshots`, v4 adds the import-provenance tables, and v5 (this close-out) adds the transaction ledger, admission audit and baseline-coverage tables. A fresh database ends at v5.

v4 adds three tables and leaves `holdings` unchanged as the current-state snapshot:

- `import_receipts` — one row per applied import or removal, with `(portfolio_id, security_id, idempotency_key, source, market_as_of, quantity, action)` and `action` constrained to `upsert` or `remove`. `UNIQUE(portfolio_id, idempotency_key)` enforces idempotency at the schema level.
- `holding_events` — the append-only audit trail, each row an `import` or `remove` event referencing its originating receipt.
- `security_aliases` — `(symbol, security_id, source, effective_from, effective_to)` windows backing effective-dated resolution.

v5 adds three more tables and leaves `holdings`, the `monitoring` table and the `monitoring_cap` trigger unchanged:

- `transactions` — signed buy/sell events `(portfolio_id, security_id, side, quantity, source, idempotency_key, occurred_at)`, `side` constrained to `buy`/`sell`, `UNIQUE(portfolio_id, idempotency_key)` enforcing idempotency; indexed on `(portfolio_id, security_id)`.
- `monitoring_admissions` — admission audit rows `(security_id, state, reason, operator, position, proposed_at)`, `state` constrained to `admitted`/`queued`, `UNIQUE(security_id)`, `position` NULL for admitted and the FIFO index for queued; indexed on `(state, position)`.
- `baseline_coverage` — `(security_id PK, covered, since)`, `covered` constrained to 0/1.

Each upgrade runs under a single immediate transaction. If any DDL or data step fails, the whole upgrade rolls back and `user_version` stays at the prior version with existing data intact (a broken v5 script leaves v4 and its holdings untouched). A foreign-key check runs before commit. A database whose version is newer than the application is rejected rather than opened. Back up an existing database before opening it with new code; the backup helper accepts only current-schema databases and does not silently upgrade archives.

## Backup and recovery

`backup(store, new_path)` and `restore(snapshot_path, new_path)` carry the v5 tables forward: a restored database preserves `transactions`, `monitoring_admissions` and `baseline_coverage` alongside the v4 import-provenance tables, holdings, observations and snapshots, and passes integrity, foreign-key and exact-schema checks. As in M1, restore revokes every credential so recovery cannot resurrect old access; re-provision users through trusted administration afterward. Neither helper overwrites an existing file.

## Idempotency and reconciliation semantics

Repeated or retried imports and removals dedupe on `(portfolio_id, idempotency_key)`. Before applying, the Store looks up an existing receipt for the key; if one is present it returns the prior `security_id` and makes no further change, so a different quantity submitted under an already-used key is ignored rather than overwriting the holding. Each applied action records exactly one receipt and one holding event, giving an auditable count that does not grow on retry. A new key applies again as a distinct action.

Receipts record the public `source` and the `market_as_of` cutoff (normalized to UTC ISO-8601) so each change states what fed it and as of when. Removal is explicit and audited: deleting a holding writes a `remove` receipt with a null quantity and a `remove` holding event. Removing a holding that is not present raises a reconciliation error and writes nothing — there is no silent success — so divergence between an external source and local state is surfaced for reconciliation. Together, `holding_events` form the ordered audit trail linking every current-state change back to the receipt that caused it.

## Evaluation

A deterministic import-provenance suite (`m2-import-provenance-baseline-v1`) is wired into `PYTHONPATH=src python -m portfolio_agent.cli eval` alongside the existing safety suite. Its synthetic cases cover an import receipt recording source and as-of, an effective-dated alias binding a symbol the validator does not know, idempotent retry applying only once, and audited explicit removal.

The M2 close-out adds a deterministic M2-completion suite (`m2-completion-baseline-v1`), so `cli eval` now runs three suites (safety, import-provenance, m2-completion) and exits nonzero if any suite has a failed case. Its five synthetic cases (`m2-001`..`m2-005`) exercise the acceptance-gate behaviors through the authorized services: a valid outside-universe security is accepted; an unknown/ambiguous symbol is quarantined (the import raises and leaves no holding or security); the 76th distinct enhancement is queued, not active; a held security retains baseline coverage with a full tier and reconciles cleanly; and a buy/sell ledger reconciles to the matching holding. The harness is fail-closed — `tests/test_m2_evals.py` mutates every expected answer and asserts all cases fail with a changed dataset hash, and rejects empty/unknown/duplicate cases. `evals/baselines/m2-completion-v1.json` records the initial result. These are regression/correctness gates that confirm the contracts above hold; they are not held-out evidence of learning, adaptation or investment results (there is no `learning_improvement` key).
